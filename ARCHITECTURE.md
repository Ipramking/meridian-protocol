# Meridian Protocol Architecture

Network: **Stellar testnet**. Contract IDs and every deploy/init transaction are in [deployments/testnet.json](deployments/testnet.json); the SDK reads the same manifest from `packages/sdk/src/deployments.ts` (generated by `scripts/deploy.mjs`).

## Components

```
 EVM chain                         Circle                     Stellar (Soroban)
 ─────────                         ──────                     ─────────────────
 user burns USDC  ──CCTP V2──▶  Iris attests  ──▶  relayer CLI checks message
 (dest domain 27,                                     │
  mintRecipient = relayer)                            │ execute_intent(intent, msg_hash, relayer)
                                                      ▼   relayer's own USDC
 Stellar user ── deposit(from, amount, vault) ──▶ MeridianRouter ──is_eligible?──▶ MeridianCompliance
                                                      │   (allowlisted vaults only)
                                                      ├── optional Soroswap leg
                                                      ▼
                                              MeridianRwaVault (router-only deposit)
                                                      │ withdraw
                                                      ▼
                                       user USDC ──SEP-10 + SEP-24──▶ anchor (fiat)
```

## Contracts

### MeridianRouter (`contracts/router`)

| Function | Who signs | What it does |
|---|---|---|
| `initialize(admin, usdc, soroswap_router, compliance, max_relayer_fee_bps)` | admin | One-time config; fee cap must be ≤ 1,000 bps |
| `set_vault(vault, enabled, requires_kyc)` | admin | Allowlist a destination vault and its KYC policy |
| `deposit(from, amount, vault)` | `from` | Pull `from`'s USDC and deposit it into an allowlisted vault for `from`; returns shares |
| `execute_intent(intent, message_hash, relayer)` | relayer | Pull `amount_in - relayer_fee` from the relayer, optionally swap, deliver to the recipient or an allowlisted vault, record the fill |
| `order_id(intent, message_hash)` | view | `sha256(message_hash ‖ xdr(intent))` |
| `get_fill(order_id)`, `get_vault(vault)`, `get_config()` | view | |
| `set_paused(bool)` | admin | Stops `deposit` and `execute_intent` |

Rules enforced in `execute_intent`: not paused; `now ≤ deadline ≤ now + 7 days`; `amount_in > 0`; `0 ≤ relayer_fee ≤ amount_in × max_relayer_fee_bps`; the order id is unfilled; the swap path starts with USDC; output ≥ `min_amount_out`; the vault is allowlisted and, if gated, the recipient is eligible.

Fill records live in persistent storage for 90 days (TTL extended on write). Because deadlines can't be more than 7 days out, a record always outlives the window in which its intent could be replayed.

Soroswap leg: Soroswap's router transfers the input token **from** `to` (the router contract) into the first pair, so the router looks up the pair with `router_pair_for` and pre-authorizes that exact transfer with `authorize_as_current_contract`. `test_swap_leg_with_strict_auth` fails without it.

### MeridianRwaVault (`contracts/vault`)

USDC share vault. Two instances are deployed: an open vault (`mvUSDC`) and a KYC-gated accredited vault (`maUSDC`).

- `deposit(amount, on_behalf_of)` requires the configured router's authorization and pulls the router's allowance.
- `deposit_direct(from, amount, on_behalf_of)` for direct deposits.
- `withdraw(owner, shares)` redeems at the current share price; it stays available while the vault is paused.
- `distribute_yield(amount)` (admin) transfers realized yield in and raises the share price for all holders. There is no accrued or hardcoded APY; on testnet no yield strategy is connected.
- Rejects deposits that would mint zero shares.

### MeridianCompliance (`contracts/compliance`)

Eligibility registry. The admin (the KYC provider) calls `set_verification(account, country, accredited, expires_at)` or `revoke(account)`. The router calls `is_eligible(account)`, which returns `false` for unknown, revoked or expired records. This is an allowlist in Meridian's own contract, not a SEP-8 regulated-asset approval server.

### MeridianPaymaster (`contracts/paymaster`)

Fee accounting: `record_sponsorship` charges a user USDC (plus a markup) and accumulates it; `rebalance_native` swaps accumulated USDC to XLM through Soroswap with the same nested-auth pattern as the router. No service sponsors transactions with fee bumps yet, so the app makes no "gasless" claim.

## Trust model

| Concern | Enforced by |
|---|---|
| Router balance can't be spent by a caller | On-chain: fills are paid from the relayer's own balance |
| Same intent filled twice | On-chain: persistent fill record keyed by intent + message hash |
| Capital sent to an arbitrary contract | On-chain: vault allowlist |
| Unverified user enters a gated vault | On-chain: compliance check inside the router |
| A fill corresponds to a real, attested CCTP burn of the right amount | **Relayer policy (off-chain).** The relayer polls Circle Iris, checks source/destination domain and amount, and refuses burns whose mint recipient is not itself. The router does not verify CCTP messages on-chain today. |
| Recipient and vault of a cross-chain intent | **Relayer input.** Today they are passed to the relayer; encoding them in CCTP hook data is on the roadmap. |

Because the relayer fronts its own funds, a relayer that fills without a matching burn loses its own money; users are not exposed. Moving attestation checks on-chain (calling Circle's Stellar message transmitter from the router) would let anyone relay without trusting relayer policy.

## Off-chain components

- **SDK** (`packages/sdk`): `MeridianClient` (vault/router reads, simulated deposit/withdraw with real resource numbers, contract-error decoding, router activity from RPC events), Iris fee quotes and CCTP V2 message parsing, DEX helpers for USDC trustlines and XLM→USDC path payments, SEP-1/10/24 helpers that validate the SEP-10 challenge and never substitute responses.
- **Relayer** (`services/relayer`): `info` and `fill` commands; see the README.
- **Web app** (`apps/web`): Freighter wallet, testnet onboarding (Friendbot, trustline, DEX swap), vault deposits/withdrawals through the router, CCTP quotes, live router activity, SEP-24 off-ramp.

## Roadmap

1. Mainnet deployment of router + open vault with real USDC (`scripts/deploy.mjs --network mainnet --yes-mainnet`), after an external review.
2. On-chain CCTP verification and hook-data intents, removing relayer trust.
3. Fee-bump sponsorship for first-time Stellar accounts.
4. A real yield source for the vaults (for example a Blend pool) instead of manager-pushed yield.
